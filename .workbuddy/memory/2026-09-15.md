# 2026-09-15

## GUI 布局重构 + 性能优化（发版 v0.1.5）

用户反馈两个问题：① 页面元素太多放不下，日志和进度条滚下去就看不见；② Mac 和低配机器上很卡。

### 问题 1：内容放不下
- **根因**：所有内容（顶栏/凭据/上传/下载/历史/日志/任务）全塞在一个 `CentralPanel` 里，
  **没有外层 ScrollArea**，超出窗口高度的部分根本滚不到。日志虽有 `max_height(180)`、
  任务虽有 ScrollArea，但在没有剩余空间时会塌缩。
- **另一个隐蔽 bug**：任务列表为空时代码直接 `return`，导致后面的日志区完全不渲染。
- **修法**：三分区布局，高度写死不依赖窗口尺寸：
  ```
  顶栏（固定 62px）→ 表单区（ScrollArea，占剩余）→ 底部停靠区（固定 38%，clamp 150~360px）
  ```
  底部停靠区内再二分：任务区 55%、日志区 45%，各自独立滚动。
  拆成 `draw_header` / `draw_forms` / `draw_dock` / `draw_task` 四个方法。

### 问题 2：卡顿（三个原因）
1. **最严重**：`load_history()` 在 **UI 线程里做同步 HTTP 请求**（切环境、点刷新、任务完成时触发），
   一次往返几百毫秒，期间界面完全冻结。
   → 改为 `load_history_async()`：后台线程下载，结果放 `Arc<Mutex<Option<Vec<HistoryItem>>>>`，
   用 `Arc<AtomicBool>` 防重入，`ui()` 每帧 `take()` 取回。
2. 传输时 `request_repaint_after(50ms)` = 20fps，每帧重建整个界面（几百个 widget）。
   → 降到 100ms（10fps），进度条足够，低配机器不再白烧 CPU。
3. 每帧渲染 200 条日志 × 3 个 label = 600 个文本。
   → 日志渲染 60 条；任务列表最多渲染 20 条（`.take(20)`）。

### 顺手修的
- 「打开所在目录」原先只调 `explorer`，**macOS 上点了没反应**。
  新增 `reveal_in_file_manager()`：Windows 用 `explorer /select,`、macOS 用 `open -R`、Linux 用 `xdg-open`。
- 「清空已完成」后重置 `history_done = 0`，否则任务数归零后不会再触发历史刷新。

### egui 0.36 API 注意（重要）
- **`TopBottomPanel` 已被移除**！现在只有通用 `Panel`（`Panel::left/right/top/bottom(id)`）+ `CentralPanel`。
- 面板的 `show_inside` 已重命名为 **`show`**，且 `show(ui, ...)` **可以直接嵌在父 Ui 里**。
  （本机最终没用面板，改用 `ui.allocate_ui` 显式分配高度，更可控。）

## 界面视觉改造（用户选定方案：美化 egui，不换 Dear ImGui）

用户问「能否接 Dear ImGui 提升性能/美观」。结论：**不换**。
- Dear ImGui 定位是调试面板，默认样式暗色密集、工具感重，**并不比 egui 好看**；
  且要全量重写 UI + 引入 C++ 编译依赖，收益不确定。
- 若真要更高视觉上限，应看 Tauri（网页技术）或 Slint（声明式 DSL），但都要重写且依赖膨胀。
- 调研：Rust 侧 Dear ImGui 绑定现有 `dear-imgui-rs`（0.17，2026-08，支持 wgpu/glow/Vulkan/docking）
  与老牌 `imgui-rs 0.12 + imgui-wgpu-rs 0.28`。
- eframe 0.36 **默认后端已是 wgpu**（macOS 走 Metal），换渲染后端不是收益点。

用户反馈的四个问题：配色土/太素、太拥挤、布局呆板、排版怪。改造内容：
- **设计色板**：PAGE_BG #F7F8FA、CARD_BG #FFF、BORDER #E5E7EB、TEXT/MUTED/FAINT 三级灰、
  ACCENT #2563EB + ACCENT_SOFT #EFF6FF、OK/WARN/DANGER 及各自的 soft 底色。
- **基础组件**（gui.rs 顶部自由函数）：`card()`（白底+细边框+圆角10+内边距）、
  `section_title()`、`form_row()`（**标签固定 54px 且右对齐**，解决输入框起点参差）、
  `primary_button()` / `ghost_button()`（主次分明）、`chip()` 状态标签。
- **输入控件**：白底 + 细边框，hover 加深、聚焦强调色描边（改 `visuals.widgets.*`）。
- **留白**：item_spacing (8,7)→(10,10)，button_padding (12,6)→(16,7)，卡片间距 12。
- **任务卡片**：类型/状态做成 chip；进度条改细（8px）且百分比移到下方明细行；
  明细统一为 `62% · 3.1MB/5.0MB · 420KB/s · 剩余 5s`。
- 所有语义色统一走常量，消除硬编码。

**egui 0.36 API 备忘**：
- `egui::Frame::NONE.fill().stroke().corner_radius().inner_margin().show()` —— Frame 没有 `new()`，用 `NONE` 常量起手。
- `ScrollArea::show_rows(ui, row_h, total, |ui, range|)` 可做列表虚拟化（日志区已用）。

## 交互细节修正（日志折叠 / 环境下拉框 bug / 记住上次环境）

1. **操作日志默认折叠**：用 `egui::collapsing_header::CollapsingState::load_with_default_open(ctx, id, false)`
   → `show_header(ui, ...)` → `header.body_unindented(|ui| ...)`。
   `show_header` 返回 `HeaderResponse`（有 `.is_open()` / `.body()` / `.body_unindented()`），
   **body 系列方法只收闭包、不收 ui**（ui 已经绑在 HeaderResponse 上）——容易用错。
   折叠状态存 `App.log_open`，底部高度按它动态分配：折叠时任务区吃满，展开后 6:4。
2. **环境下拉框 bug（用户发现：没配 outer 也能看到）**：`App::new` 里
   `if !envs.contains(&env) { envs.push(env.clone()); }` —— 不管 ini 里有没有都把默认环境塞进列表。
   改为只列 ini 中真实存在的 section（排除 common）；
   ini 无任何环境段时显示「ini 中未配置环境段」提示而不是空下拉框。
3. **记住上次选择的环境**：新增 `state_path()` / `load_last_env()` / `save_last_env()`，
   状态写到 **iobs.ini 同目录的 `sync-iobs.state`**（内容 `last_env=xxx`）。
   - 关键取舍：**不回写 iobs.ini** —— `write_sections` 会按解析结果重建整个文件，
     **用户手写的注释会被抹掉**。状态单独存小文件最安全；写失败静默忽略（exe 在只读目录时）。
   - 已把 `sync-iobs.state` 加入 .gitignore。
   - 环境优先级：上次使用的 > 配置里的默认 > 第一个环境段；确定后用 `resolve_sections_relaxed` 重建 cfg。

## 修复：上传后历史记录不刷新（v0.1.6）—— 异步改造引入的竞态

上一版把历史拉取改成异步后，用户反馈「上传后不更新历史了」。

- **根因**：刷新条件写成 `已完成任务数 > history_done`，而 `history_done` 是**乐观递增**的。
  1. 若此刻已有一次拉取在飞（比如启动时那次），`load_history_async` 因 `swap(true)` 返回 true 而直接跳过；
     但计数已经加过了 → **再也不会重试**。
  2. 更隐蔽：那次在飞的拉取可能发起于上传写入之前，返回的本来就是旧数据。
- **正确做法**：刷新时机的判断必须发生在「写回成功」之后，且要能重试。
  - 由**上传线程**在 `record_upload` 成功后 `history_refresh.store(true)`，
    保证「先写完再拉取」的时序（界面无法可靠推断这个时刻）。
  - `load_history_async` 改为**返回 bool**（是否真的发起）；UI 里若返回 false
    且 `history_loading` 为 true（在飞），把标记放回去、下一帧再试。
  - 若因缺凭据返回 false，则丢弃标记，避免永远挂着。
- **两个健壮性加固**：
  - `LoadingGuard`（Drop 里复位 `loading`）：线程内 panic 也不会让标记卡在 true
    （否则历史从此再也不刷新，且极难排查）。
  - `history_pending` 锁中毒时用 `poisoned.into_inner()` 恢复数据，而不是静默丢弃。
- 切环境 / 点「刷新」统一走 `request_history_refresh()`。
- 发版 v0.1.6，run `34987246147` 全绿。

**教训**：把「UI 线程同步调用」改成「后台异步 + 结果回传」时，
除了搬走阻塞调用，还必须重新设计**触发条件的时序与重试**——
原来靠「状态变化」触发的隐式约定，在异步下会因为「跳过 = 永久丢失」而失效。

## 踩坑
- 用 Python 文本模式写文件会把 `\n` 转成 `\r\n`（Windows 默认），曾让 Cargo.lock 从 112794 涨到 117326 字节。
  写 Cargo.toml / Cargo.lock 这类文件要用 `newline=''` 或直接二进制写。
- 大段代码替换时 Edit 工具常因空白/换行差异匹配失败；改用 Python 按标记定位
  （`t.index(marker)`）切片替换更可靠。
