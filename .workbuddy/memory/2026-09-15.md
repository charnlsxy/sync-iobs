# 2026-09-15

## GUI 布局重构 + 性能优化（发版 v0.1.5）

用户反馈两个问题：① 页面元素太多放不下，日志和进度条滚下去就看不见；② Mac 和低配机器上很卡。

### 问题 1：内容放不下
- **根因**：所有内容（顶栏/凭据/上传/下载/历史/日志/任务）全塞在一个 `CentralPanel` 里，
  **没有外层 ScrollArea**，超出窗口高度的部分根本滚不到。日志虽有 `max_height(180)`、
  任务虽有 ScrollArea，但在没有剩余空间时会塌缩。
- **另一个隐蔽 bug**：任务列表为空时代码直接 `return`，导致后面的日志区完全不渲染。
- **修法**：三分区布局，高度写死不依赖窗口尺寸：
  ```
  顶栏（固定 62px）→ 表单区（ScrollArea，占剩余）→ 底部停靠区（固定 38%，clamp 150~360px）
  ```
  底部停靠区内再二分：任务区 55%、日志区 45%，各自独立滚动。
  拆成 `draw_header` / `draw_forms` / `draw_dock` / `draw_task` 四个方法。

### 问题 2：卡顿（三个原因）
1. **最严重**：`load_history()` 在 **UI 线程里做同步 HTTP 请求**（切环境、点刷新、任务完成时触发），
   一次往返几百毫秒，期间界面完全冻结。
   → 改为 `load_history_async()`：后台线程下载，结果放 `Arc<Mutex<Option<Vec<HistoryItem>>>>`，
   用 `Arc<AtomicBool>` 防重入，`ui()` 每帧 `take()` 取回。
2. 传输时 `request_repaint_after(50ms)` = 20fps，每帧重建整个界面（几百个 widget）。
   → 降到 100ms（10fps），进度条足够，低配机器不再白烧 CPU。
3. 每帧渲染 200 条日志 × 3 个 label = 600 个文本。
   → 日志渲染 60 条；任务列表最多渲染 20 条（`.take(20)`）。

### 顺手修的
- 「打开所在目录」原先只调 `explorer`，**macOS 上点了没反应**。
  新增 `reveal_in_file_manager()`：Windows 用 `explorer /select,`、macOS 用 `open -R`、Linux 用 `xdg-open`。
- 「清空已完成」后重置 `history_done = 0`，否则任务数归零后不会再触发历史刷新。

### egui 0.36 API 注意（重要）
- **`TopBottomPanel` 已被移除**！现在只有通用 `Panel`（`Panel::left/right/top/bottom(id)`）+ `CentralPanel`。
- 面板的 `show_inside` 已重命名为 **`show`**，且 `show(ui, ...)` **可以直接嵌在父 Ui 里**。
  （本机最终没用面板，改用 `ui.allocate_ui` 显式分配高度，更可控。）

## 踩坑
- 用 Python 文本模式写文件会把 `\n` 转成 `\r\n`（Windows 默认），曾让 Cargo.lock 从 112794 涨到 117326 字节。
  写 Cargo.toml / Cargo.lock 这类文件要用 `newline=''` 或直接二进制写。
- 大段代码替换时 Edit 工具常因空白/换行差异匹配失败；改用 Python 按标记定位
  （`t.index(marker)`）切片替换更可靠。
