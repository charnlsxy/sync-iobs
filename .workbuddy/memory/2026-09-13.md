## http.rs 重试逻辑 bug 修复（同日续）

- **坑**：`get_into`（下载）把所有错误（含 4xx 的 `ureq::Error::Status`）丢进通用 `Err(e)` 分支重试 3 次 → 首次上传时 `load_history` 因 key 不存在收 612，被误重试 3 次 + 误导「重试」字样。
- 根因是重试判定写成了 `code >= 500`（把服务端自定义码 **612** 也当成 5xx 可重试）。正确 5xx 区间应 `500..=599`。`post_bytes` 也有同一 bug（当时没触发，因上传多返 4xx）。
- 修复：`get_into` 与 `post_bytes` 统一改成 `retryable = (code >= 500 && code < 600) || code == 429`；4xx/612 立即失败不重试。修复后首次上传不再有冗余重试，且 612/402 等明确错误即时返回。

### 关键坑 1：token 类型 —— 细粒度 vs 经典
- 用户第一次给的 `ghp_xx...` 竟然是**细粒度 token**（GitHub 现在也用 `ghp_` 前缀了！）。
  - 判别法：`GET /user` 响应头有 `X-OAuth-Scopes` = 经典 token（会列出权限项）；**没有该头** = 细粒度 token。
  - 细粒度只读时：读 API 全 200，但**所有写操作统一返回 404**（而非 403），极易误判为「仓库不存在」。
- 第二个 token 是经典 token，`X-OAuth-Scopes` 含 `repo, workflow, ...`，全部操作通过。

### 关键坑 2：推送内容与实际源码不一致（本次 CI 失败根因）
- **症状**：三平台 `cargo test` 全失败，本地却 5/5 通过。
- **根因**：`git add -A` 之后、`git commit` 之前，`src/gui.rs` 与 `src/iobs.rs` 被外部改动（进行中的「GUI 日志面板」功能，把 `Client::new(cfg)` 改成 `Client::new(cfg, log)`）。提交的是**中间快照**，`gui.rs` 旧版调 1 参数、`http.rs` 新版要 2 参数 → `error[E0061]` × 4。
- **教训**：`git add` 与 `git commit` 之间源码可能被改；推送后务必用 API 核对远程文件与本地是否逐字节一致（`/contents/{path}` + base64 解码比对）。
- **修复**：因 `git push` 反复 SSL/502 失败，改用 **Git API 三步绕过**：`POST /git/blobs` → `POST /git/trees`(base_tree) → `POST /git/commits` → `PATCH /git/refs/heads/main`。这条路可靠且不受 push 网络影响。

### 关键坑 3：Actions 构建日志的下载方式
- `GET /repos/{o}/{r}/actions/jobs/{job_id}/logs` 会 **302 到 Azure Blob 预签名 URL**。
- **Bearer / token 认证在该端点都会失败**（403 AuthenticationFailed / 401），因为重定向后的 URL 自带签名，**必须剥掉 Authorization 头**。
- 解法：自定义 `HTTPRedirectHandler.redirect_request`，重定向时 `headers.pop('Authorization')`，然后跟随后读取（响应可能 gzip）。

### 关键坑 4：Actions 日志被折叠
- 日志里 `##[group]` / `##[endgroup]` 把步骤输出折叠，直接 tail 看不到错误；要**正则搜 `error(\[E\d+\])?:`** 定位真正的编译错误行。

- 安全闸门初版有 bug：非 git 仓库里 `git check-ignore` 返回非 0 → 误报。修法：**先 `git init` 再扫描**，并用 `git check-ignore -q` 判断忽略状态。

## 关键坑 5：GUI 与 CLI 产物同名互相覆盖（用户发现，已修）

- **用户反馈**：「gui 版本也只有 600 多 kb，还是 cli 版面」—— 一针见血。
- **根因**：workflow 里 GUI 和 CLI 两个 build 步骤输出到**同一个路径** `target/<triple>/release/sync-iobs(.exe)`。cargo 第二次（`--no-default-features`）编译时 feature 变化会重编并**覆盖同名产物**。打包步骤再从这个路径取文件 → gui 包里装的是 CLI。
- **证据**：v0.1.0 的 `gui.zip` 仅 0.35MB，与 CLI 单文件 0.68MB 压缩后一致；修复后 gui.zip 4.11MB、包内 exe 8.47MB。
- **修法**：每编完一个变体**立刻拷到 `staging/` 并改名**（`sync-iobs-gui` / `sync-iobs-cli`），后续打包统一从 staging 取。
- **加固**：新增「尺寸校验」步骤 —— GUI 产物若不大于 CLI 就直接 `exit 1`，让同类问题在 CI 暴露而不是静默发出。
- **验证**：下载 Release 的 gui.zip 解压，包内 exe 8.47MB 且含 `egui`/`eframe`/`winit`/`glutin` 特征串 → 确认是真 GUI。
- **通用教训**：同一 workflow 里编译同一 crate 的多个 feature 变体时，产物必然同名，**必须编完即改名隔离**；并用断言守护（尺寸/特征串）。

## 待改进：main 与 tag 重复触发（用户指出）

- 现状 `on.push` 同时监听 `branches:[main]` 和 `tags:[v*]`，导致**同一 commit 跑两遍完整流水线**：
  - main 那次：test + build，release 被 skip
  - tag 那次：test + build + release ← 前两步纯属重复
- 实测：commit `fc0c35f4` 上 run `34762664026`(main) 与 `34763186361`(v0.1.1) 各跑一次。
- 解决方案待用户定：
  - A（省事）：main 只跑 test；tag 跑 test+build+release。缺点：main 推送不再验证能否编译。
  - B（省资源）：main 跑 test+build 并留 artifacts；tag 只跑 release，用 `actions/download-artifact@v4` 带 `run-id` 从同 SHA 的 main 运行取产物。缺点：多一步查 run-id，且 tag 指向非 main 的 commit 时会失败。
- **用户决定：方案 A 的变体 —— main 完全不触发，全部由 tag 触发。** 已改 `on.push` 只留 `tags: ["v*"]`（PR 仍跑测试但 `if` 条件使其不发布；保留 `workflow_dispatch` 手动验证）。
- 同时加了两个守护：release 里校验 **tag 名与 Cargo.toml 版本一致**；解压产物校验 **GUI 包内 exe 必须明显大于 CLI 且含 egui/eframe 特征串**。
- macOS Info.plist 的版本号改为从 Cargo.toml 读取（原硬编码 0.1.0）。
- **版本号已 0.1.0 → 0.1.1**，`Cargo.toml` 与 `Cargo.lock` 同步改（CI 用 `--locked`，只改一处会构建失败）。改动 commit `d42ed41` 已本地提交，**用户要求暂不推送**，远程仍停在 `fc0c35f4`。

## 关键坑 6：全新 exe 未填 ak/sk 却能看到历史记录（用户提问）

- **现象**：用户下载的全新执行文件，没输入 ak/sk，界面里却已有历史记录。
- **排查结论：不是构建泄露，而是配置自动发现。**
  - ① 扫描 v0.1.1 Release 的 windows cli exe（614912 B）→ **不含**真实 ak/sk 特征串；`Config::default()` 的 ak/sk 也是空串；分发包里的 `iobs.ini` 是空凭据模板。**排除内嵌凭据**。
  - ② 历史记录**不存本地**：它是服务端的一个 JSON 对象，固定 key `HISTORY_KEY = "cztesthistoryupload10"`（`src/iobs.rs:20`）。GUI 启动时 `App::new` → `app.load_history()`（`gui.rs:136`）→ `io.load_history()` 下载该 key 并解析（`gui.rs:260`、`iobs.rs:314`）。
  - ③ 下载需要 ak/sk，而 `find_config()`（`config.rs:121`）按序自动查找：`--config` → **当前工作目录 `iobs.ini`** → **exe 同目录 `iobs.ini`** → `%APPDATA%\sync-iobs\iobs.ini`。
  - ④ 本机实测：项目根 `iobs.ini` 与 **`dist\iobs.ini`（1118 B，含真实 ak）都存在**；`%APPDATA%\sync-iobs\iobs.ini` 不存在。exe 放在 `dist\`（或从项目根启动）→ 静默加载真实凭据 → 认证成功 → 拉回历史。
- **设计缺陷**：GUI 只调用 `default_config_path()` 用于保存（`gui.rs:114`），**不显示当前加载的是哪个配置文件、凭据从哪来**，所以「全新 exe 却有凭据」看起来像灵异事件。而且「当前工作目录」这一档查找会在任意目录误用无关 ini。
- **待改进选项**（未实施）：顶栏显示「当前配置：<路径>」；去掉 CWD 查找档；首次从文件读到凭据时提示来源；历史可做本地缓存（离线可看）。
- **提醒用户**：`dist\iobs.ini` 与项目根 `iobs.ini` 都含真实凭据，**别把整个 `dist\` 目录打包外发**（仓库侧已 gitignore）。
