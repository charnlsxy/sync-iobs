# 2026-09-14

## 修复 macOS 中文乱码 + CI 仅 tag 触发（发版 v0.1.3）

### 问题 1：macOS 上中文全是方块/乱码
- **根因**：`src/gui.rs` 的 `setup_fonts()` 候选列表**只有 4 个 Windows 路径**
  （`C:\Windows\Fonts\simhei.ttf` / `Deng.ttf` / `msyh.ttc` / `simsun.ttc`）。
  macOS 上一个都匹配不到 → 没挂任何 CJK 字体 → 中文渲染成方块/乱码。
- **先确认可行性**：egui 0.36 的 `FontData` 有 `index` 字段，底层用
  **`skrifa::FontRef::from_index`** 解析 —— 原生支持 `.ttc` 字体集合，
  所以 macOS 的 `PingFang.ttc`（ttc）可以直接用，取 index 0（PingFang SC 字面）。
- **修法**：候选列表改成跨平台三段：
  - Windows：simhei / Deng / msyh / simsun
  - macOS：`/System/Library/Fonts/PingFang.ttc`、STHeiti Medium/Light、Hiragino Sans GB、
    `Supplemental/Songti.ttc`、`Supplemental/STHeiti Medium.ttc`、`/Library/Fonts/Arial Unicode.ttf`
  - Linux：`NotoSansCJK-Regular.ttc`、文泉驿 zenhei/microhei、文鼎 uming
  - 加了空文件跳过（某些 Supplemental 目录在旧系统上不存在）
- `setup_fonts` 改为**返回 `Option<String>`**（实际加载的字体路径），经 `run()` 传给 `App::new`，
  启动时写入日志面板；没加载到就打 WARN「未找到系统中文字体，界面中文可能显示为方块」。
  这样以后再出乱码，看日志就知道挂上了哪个字体。

### 问题 2：分支/PR 不要自动部署
- workflow 的 `on` 去掉 `pull_request` 触发器，现在只剩：
  ```yaml
  on:
    push:
      tags: ["v*"]
    workflow_dispatch:
  ```
- `workflow_dispatch` 保留：只跑测试与编译，**不会发版**（`release` job 有
  `if: startsWith(github.ref, 'refs/tags/v')` 拦截）。
- 实测确认：推 main（`13c25b96`）后没有任何 run；只有打 `v0.1.3` tag 才跑了一次完整流水线。

### 发版 v0.1.3
- 版本号 `0.1.2 → 0.1.3`（`Cargo.toml` + `Cargo.lock` 同改，`--locked` 才过得去）。
- 提交 → API 推送 main（`13c25b96`）→ 建 tag `v0.1.3` → run `34845313750` **7 个 job 全绿**。
- Release 附件 7 个：windows gui.zip 4.11MB / cli.exe 0.59MB；
  macos-arm64 gui.zip 3.28MB / cli 0.72MB；macos-x86_64 gui.zip 3.73MB / cli 0.72MB；SHA256SUMS.txt。

## 沿用经验（本次复用，很顺）
- 推送一律走 `scripts/gh-api-push.py`（`git push` 在这台机器上非快进 + SSL/502，基本不可用）。
- 发版固定动作：改两处版本号 → `cargo check --offline --locked` → API 推 main → 建 `vX.Y.Z` tag → 轮询 run → 核对 Release。
- 改代码后先本地 `cargo check`（默认 + `--no-default-features`）+ `cargo test`，再推送，避免推编译不过的版本。
